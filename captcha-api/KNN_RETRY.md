# 首次识别失败后使用 KNN 重试

机器人首次仍调用原来的 `/recognize`。启用自动验证时，首次没有可点击答案，或游戏再次返回同一
图片验证码，会在原有随机/人工兜底前请求一次 KNN。同一个机器人、同一图片最多尝试一次；
题目“第 N 个表情”以原始候选位置取答案。KNN 与已失败答案相同时不再按同一答案提交。

手动模式不调用 KNN；半自动、全自动模式都可尝试一次。KNN 仍无可用答案时，半自动转人工，
全自动继续现有兜底。会员/配额拒绝不会切换 KNN 绕过限制；按钮点击异常仍只按原按钮重试一次，
不会被当成图像识别错误。接口连接/读取超时分别为 5/15 秒。
等待期间切到手动模式，或收到不同图片的新验证码时，旧识别结果会取消点击。

全局配置 `captcha.knn-retry-enabled` 默认 `true`，可设置 `false` 恢复原来的失败处理方式。

KNN 明确失败可单独归档并在 `/admin/knn-review` 人工纠错，确认后手动发布到索引；详见 `KNN_REVIEW.md`。

KNN 重试可在 `/admin/knn-background` 配置整图背景抑制，默认关闭；保存后下一次请求生效。
首次主模型保持原样，KNN 继续从原图取分类特征，原索引可直接使用。预览、限制与部署见 `KNN_BACKGROUND.md`。

## 验证统计

发送原有命令 `验证统计`，主模型和 KNN 重试会分别展示累计/今日的调用次数、成功、失败、
未确认和成功率。调用次数按机器人实际发起的对应请求计数，KNN 不会重复计入主模型调用。

- 成功：自动提交答案后，收到同一群内明确指向当前机器人账号的游戏验证成功/通过/验证奖励回执，
  或整段为“奖励5574灵石”一类验证码奖励的回执。支持 Markdown 正文与单独的 @ 消息段，
  悬赏、宗门、秘境等带任务前缀的普通奖励不算成功。
  按钮接口返回成功只代表提交成功，暂列“未确认”，不会直接提高成功率。
- 失败：服务正常响应但没有可用答案，或自动提交后收到验证失败回执、在有效期内再次收到
  同一验证码图片。重复消息/回执只结算一次；KNN 给出之前失败的相同答案也计失败。
- 未确认：接口/配额异常、点击异常、验证码过期、超过 5 分钟无确认、新验证码替换旧验证码、
  或切到手动模式后没有确认的自动尝试。不会按“没再出现验证码”推测成功。
- 成功率为 `成功 / (成功 + 失败)`；未确认不进入分母。今日数据按请求发起日期统计。
  KNN 只接收主模型失败后的较难样本，因此两个成功率反映各自阶段效果，不能当作同一批样本的模型对比。

随机兜底成功不归入主模型或 KNN。未发起自动识别的人工验证不进入分项统计；通过机器人
控制命令人工点击或由旧识别流程接管时，原自动尝试保持未确认，后续回执不再归因给该模型。
直接在 QQ 客户端人工点击无法通过现有回执区分来源，建议先切到手动模式再接管。
输出只保留主模型、KNN 重试两个区块，中间空一行；没有已确认样本时显示 `0.00%`。
旧版计数无法恢复来源，保留在存储中，不显示、不并入新分项。原有 `重置验证统计` 会一起清空两项；
分项计数沿用任务数据文件保存，重启后保留累计值，未结算尝试保持“未确认”。

## 服务端协议

沿用同一地址和身份信息，主请求仍为 `{"url":"..."}`，KNN 请求为
`{"url":"...","recognizer":"knn"}`。QQ 仍通过原来的 `?qq=` 传递，认证、会员和实际调用计数不变，
第二次调用会照常计次。无需单独开放一个绕过鉴权的 KNN 接口。

KNN 分支复用现有检测器、排序和分类网络的 avgpool 特征，使用原框/15% 扩框的归一化特征拼接
进行 5 近邻加权投票。KNN 可由后台开启检测前背景抑制；不接入去线条试验，不改变首次识别及检测阈值。

响应包含 `recognizer: "knn"`、`knnAppliedIndices`（实际通过 KNN 的表情位置，从 0 开始）、
`knnStatus` 及逐项 KNN 结果。未覆盖、置信不足的候选保留原标签和位置；机器人只有在题目目标
位置确实包含在 `knnAppliedIndices` 中时才使用该答案。旧后台忽略新字段时，机器人不会误认为
已经调用 KNN。索引缺失/不匹配时返回 unavailable，不伪造 KNN 成功结果。

## 当前索引

由 618 张人工确认图片构建，共 2486 个裁图、80 维特征。覆盖 12 类：书本、兔子、图钉、汽车、
沙漏、电池、电脑、苹果、葡萄、西瓜、鲸鱼、鸡头。特征文件不包含原图、会员信息或样本 ID。

为避免把其余类别硬猜成上述 12 类，当前仅对主分类器落在已覆盖类别内的候选应用 KNN；
因此当前方案不能保证纠正主分类器误判成未覆盖类别的情况。
沿用已有相似度/差值/投票门槛 0.5/0/0，这些是检索门槛，不是正确率；没有对新索引声称准确率。
模型配置、权重及特征文件均核对 SHA-256，索引和元数据须成对发布。

## 部署

1. 先更新识别服务的 `routes/api_routes.py`（`captcha_api.py` 实际加载的路由）、根目录兼容入口
   `api_routes.py`、`config.py`，新增 `knn_classifier.py` 和整个 `knn/` 目录，
   然后重启识别服务。沿用现有模型文件和依赖，无需修改会员/白名单/计数文件。
2. 再更新机器人 JAR 并重启。需要两个部分都更新才会生效；只更新 Java 时，旧识别服务会按
   未支持 KNN 处理并继续原有兜底。
3. 日志出现“首次验证码识别失败，使用KNN重试一次”表示机器人确实发起第二次调用。
   服务端响应目标题目的位置应在 `knnAppliedIndices` 中。

若服务代码随 Docker 镜像打包，需要重建镜像；只修改未挂载的宿主目录不会更新容器中的代码。

模型路径仍由现有 CLASSIFY_CONFIG/CLASSIFY_WEIGHTS/CLASSIFY_LABELS 控制，KNN 路径可通过
KNN_INDEX_PATH、KNN_REPORT_PATH 配置。Docker 镜像必须包含 knn/ 目录。

人工标注增加后，在识别服务目录构建新索引：

```powershell
python build_knn_index.py --dataset-root "D:\Java\图标识别交接包_20261022\图片识别\datasets"
```

只读取 `ground_truth_confirmed: true` 的记录，不使用错误上报中的旧预测答案，不修改数据集。
构建后将 `knn/reference_index.npz` 和 `knn/reference_meta.json` 一起更新；运行时按文件变更重载。

离线测试：`python -m unittest discover -s tests -p test_knn_retry.py -v`。
