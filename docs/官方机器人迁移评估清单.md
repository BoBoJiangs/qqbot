# 官方机器人迁移评估清单

> 评估时间：2026-09-30
> 背景：个人号 + SnowLuma 方案无法发送带真按钮的 markdown 卡片（官方机器人专属能力），
> 评估将现有系统迁移/部分迁移到 QQ 官方机器人（q.qq.com）的可行性与工作量。
> 关联文档：[SnowLuma迁移与兼容修改记录.md](SnowLuma迁移与兼容修改记录.md)

---

## 一、结论速览

| 迁移策略 | 可行性 | 说明 |
|----------|--------|------|
| **整体迁移** | ❌ 不可行 | 官方机器人能力模型与游戏自动化根本冲突（见第二节），且违反开放平台规范，账号会被封禁 |
| **双轨制（推荐）** | ✅ 可行 | 官机做"查询展示"（带真按钮的卡片），个人号继续跑自动化，共用后端服务 |
| 纯计算层独立 | ✅ 可行 | 丹方匹配/价格服务抽出为独立 HTTP 服务，两边共用 |

---

## 二、整体迁移为什么不可行（能力冲突清单）

| 现有功能 | 依赖的私聊/群聊能力 | 官方机器人的限制 | 结果 |
|----------|--------------------|------------------|------|
| 监听小小(3889001741)的按钮卡片/验证码 | 群聊**全部消息** | 群聊只推送 @机器人 的消息 | ❌ 触发链失效 |
| 自动点击按钮（click_inline_keyboard_button） | 操作他人消息 | 无法操作非自身消息 | ❌ 完全没有 |
| 验证码自动识别+点击 | 收到卡片图+按钮 | 同上 | ❌ 完全没有 |
| 定时任务（04:36 宗门/08:05 悬赏/秘域提醒等） | 任意时间主动发群消息 | 主动消息有月度配额与频控 | ❌ 额度撑不住 |
| 灵石赠送/接收码流程 | 监听玩家接收码并回复 | 只能响应 @机器人 | ❌ 流程断裂 |
| 发送 markdown/按钮卡片 | — | 需申请模板权限、内容过审 | ⚠️ 有，但受限 |
| 群管/禁言/踢人 | 群管理 API | 官机无群管理权限 | ❌ 没有 |
| 游戏自动化本质 | 模拟真人操作 | 明确违反开放平台规范 | ❌ 封号风险 |

---

## 三、双轨制架构（推荐方案）

```
                     ┌──────────────────────────┐
   用户 @官机 查询 → │  官方机器人 (q.qq.com)    │ → 回复带真按钮的 markdown 卡片
                     │  展示层：查丹方/查价格     │
                     └────────────┬─────────────┘
                                  │ HTTP 调用（共用后端）
                                  ▼
                     ┌──────────────────────────┐
   个人号自动化 →    │  后端服务（现有代码抽取）  │
                     │  丹方匹配/价格计算        │
                     └────────────┬─────────────┘
                                  │
                                  ▼
                     ┌──────────────────────────┐
                     │ SnowLuma + 个人号（现状） │ → 监听/点击/定时任务，原样保留
                     └──────────────────────────┘
```

### 3.1 官方机器人侧（新增）

| 事项 | 说明 | 预估工作量 |
|------|------|-----------|
| 注册开放平台账号 | q.qq.com，需企业或个人主体认证 | 0.5 天（审核另计） |
| 创建机器人并申请权限 | 群聊场景、markdown 模板权限、按钮权限逐项申请 | 1-3 天（审核周期不可控） |
| markdown 模板设计 | 按钮卡片需用平台模板语法，内容要过审 | 1-2 天/模板 |
| 机器人服务端 | 接收 WebSocket 事件回调 + 回复 | 2-3 天 |
| 接入后端服务 | 调用 3.2 抽出的查询接口 | 0.5 天 |

### 3.2 后端服务抽取（从现有代码剥离）

| 模块 | 现有文件 | 迁移方式 | 工作量 |
|------|----------|----------|--------|
| 背包丹方匹配 | `HerbBackpackMatchService`（730行）+ `DanRecipeBlueprint` + `HerbBackpackMatchResult` | 抽成 Spring Boot REST 服务：`POST /api/match`（入参药材清单+成丹数，返回匹配结果 JSON） | 1-2 天 |
| 群级丹方配置 | `GroupRecipeMatchConfigService` | 随匹配服务一起迁移，配置改走 HTTP 参数 | 0.5 天 |
| 丹方/炼金价值查询 | `DanRecipeQueryService` | 保留在主程序（个人号用），匹配服务内嵌一份只读副本 | 0.5 天 |
| 药材价格 | `ProductPriceResponse` + H2 数据 | **留在主程序**（实时行情由个人号链路维护），匹配服务按需调主程序接口或读共享文件 | 0.5 天 |
| 价格数据文件 | `properties/坊市价格.txt`（JSON快照） | 两个服务共享读取 | - |

### 3.3 个人号侧（不动）

现有全部功能保持现状：SnowLuma 三开、java-bot、验证码识别、定时任务、提醒体系。
仅需在 `HerbBackpackMatchService.submitMatch` 里加一个开关：走本地匹配 or 转发到新服务（灰度用）。

## 四、官机能做什么 / 不能做什么（双轨制下的分工）

### ✅ 适合放到官机（被动查询 + 按钮交互）

| 功能 | 交互形式 |
|------|----------|
| 查丹方（含炼金/坊市利润） | @官机 "查丹方 创世丹" → markdown 卡片 + 按钮（炼金价/坊市价切换） |
| 查药材价格 | @官机 "查价 天麻翡石" → 价格卡片 + "近7天趋势"按钮 |
| 查背包匹配 | 用户把背包转发给官机（私聊）→ 返回匹配结果卡片 + "匹配炼金丹/匹配坊市丹"按钮 |
| 使用帮助 | 按钮导航式菜单 |

### ❌ 必须留在个人号（自动化，官机做不了）

- 全部监听类：小小说明卡片、验证码、玩家接收码、群消息统计
- 全部定时类：宗门任务、悬赏任务、秘域/秘境/灵田/传功提醒、行情同步
- 全部操作类：自动点按钮、自动炼丹、自动购买、灵石赠送
- 群管理、消息转发到控制群

## 五、风险与成本备忘

1. **审核风险**：游戏辅助类内容过审难度大，卡片文案避免"自动/代练/脚本"字样，只做"查询工具"定位；
2. **配额风险**：官机主动消息月配额有限，双轨制下官机只做被动回复，基本不受影响；
3. **维护成本**：双入口意味着一次功能改动可能要改两处（后端服务化后可收敛为一处）；
4. **废弃成本**：若只为按钮按钮体验而迁移，投入 5-10 人天换来的只是展示升级，先明确需求再动工；
5. **号池风险不变**：个人号侧的封号/风控风险与本次迁移无关，维持现状（见 SnowLuma 文档）。

## 六、行动建议（按优先级）

1. [ ] 先明确"按钮"的真实需求场景——如果只是给玩家看匹配结果，现有"文本模拟按钮"够用，可暂不迁移；
2. [ ] 若确定要做：注册开放平台 + 申请群聊/markdown/按钮权限（审核周期最长，先启动）；
3. [ ] 抽取匹配服务为独立 REST 服务（个人号与官机共用）；
4. [ ] 开发官机回调服务（WebSocket 事件 + 按钮点击回调）；
5. [ ] markdown 模板设计与报审；
6. [ ] 联调上线，个人号链路保持原样作为兜底。
